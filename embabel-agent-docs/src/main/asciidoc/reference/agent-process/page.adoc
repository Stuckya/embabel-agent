[[reference.agent-process]]
=== The AgentProcess

An `AgentProcess` is created every time an agent is run.
It has a unique id.

[[reference.agent-process__execution-modes]]
=== Execution Modes

Embabel supports two execution modes for agent processes, controlled by the
`embabel.agent.platform.process-type` property.

[[reference.agent-process__simple]]
==== SimpleAgentProcess (Default)

`SimpleAgentProcess` is the default execution mode.
On each planning tick it selects the single best action from the current plan
and runs it to completion before replanning.

This sequential approach is predictable and easy to reason about:
actions never run in parallel and the blackboard is always in a consistent state
when the next action begins.

[[reference.agent-process__concurrent]]
==== ConcurrentAgentProcess

`ConcurrentAgentProcess` extends `SimpleAgentProcess` and runs *all currently
achievable actions in parallel* on each planning tick.

Instead of picking one action per tick, it finds every action in the plan that
is achievable given the current world state and launches them concurrently using
the platform's `Asyncer` abstraction (backed by Spring's managed task executor
with virtual threads).
Once all launched actions have completed the process replans, and the cycle repeats.

This is useful when an agent has independent sub-tasks that can proceed simultaneously—
for example, enriching multiple data items in parallel, or running several
analysis steps whose outputs do not depend on each other.

===== Activating ConcurrentAgentProcess

Set the following property in your application configuration:

[source,yaml]
----
embabel:
  agent:
    platform:
      process-type: CONCURRENT
----

or in `application.properties`:

[source,properties]
----
embabel.agent.platform.process-type=CONCURRENT
----

The default value is `SIMPLE`.

===== Replanning in Concurrent Mode

Both `SimpleAgentProcess` and `ConcurrentAgentProcess` support
`ReplanRequestedException`, which an action can throw to signal that the agent
should update the blackboard and replan before proceeding.

In `ConcurrentAgentProcess`, multiple concurrently running actions may throw
`ReplanRequestedException` at the same time.
When this happens only the first request is honoured—its blackboard updates
are applied and the triggering action is blacklisted for the next planning
cycle to prevent an immediate infinite loop.
The remaining requests are silently dropped, as they ran in a context that is
about to be replanned anyway.

The blacklist is cleared automatically after a successful planning cycle.
If no plan can be found while a blacklist is active, the blacklist is cleared
and planning is retried, ensuring the agent does not become permanently stuck.

===== Choosing an Execution Mode

[cols="1,2,2",options="header"]
|===
|Mode |When to use |Trade-offs

|`SIMPLE`
|Most agents; sequential pipelines; when action order matters
|Predictable; easier to debug; no concurrency overhead

|`CONCURRENT`
|Independent parallel sub-tasks; fan-out/fan-in patterns; throughput-sensitive workloads
|Higher throughput; requires actions to be safe to run concurrently against a shared blackboard
|===

=== ProcessOptions

Agent processes can be configured with `ProcessOptions`.

`ProcessOptions` controls:

* `contextId`: An identifier of any existing context in which the agent is running.
* `blackboard`: The blackboard to use for the agent.
Allows starting from a particular state.
* `test`: Whether the agent is running in test mode.
* `verbosity`: The verbosity level of the agent.
Allows fine grained control over logging prompts, LLM returns and detailed planning information
* `control`: Control options, determining whether the agent should be terminated as a last resort. `EarlyTerminationPolicy` can based on an absolute number of actions or a maximum budget.
* Delays: Both operations (actions) and tools can have delays.
This is useful to avoid rate limiting.
* `ephemaral`: blocks Agent Process from persisting in Agent Process Repository and from spawning child processes (light-weighted agent process)
* `toolCallContext`: Out-of-band metadata (e.g., auth tokens, tenant IDs, correlation IDs) passed to all tool invocations during the process.
This context propagates through the entire tool pipeline—including decorator chains and MCP tools—without being exposed to the LLM.
Set via `withToolCallContext()`:

[tabs]
====
Java::
+
[source,java]
----
var processOptions = new ProcessOptions()
    .withToolCallContext(Map.of(
        "authToken", bearerToken,
        "tenantId", tenantId
    ));
----

Kotlin::
+
[source,kotlin]
----
val processOptions = ProcessOptions()
    .withToolCallContext(ToolCallContext.of(
        "authToken" to bearerToken,
        "tenantId" to tenantId,
    ))
----
====

See <<reference.tools__tool-call-context>> for how tools receive this context.

[[reference.agent-process__evolution-options]]
==== EvolutionOptions

`ProcessOptions` can also carry `EvolutionOptions`, an experimental overlay for
evolving a process agenda at planning ticks.
The agenda is projected into the effective planning system for the process; it
does not mutate the agent's declared goals.
The current POC evolves agenda entries over the `AgentScope` created for the
process.
It does not add new agents, actions, or capability modules to an already-running
process.

`EvolutionOptions` is the current low-level POC surface.
This evolving-mode material describes local experimental work in the
`codex/evolving-mode` branch, not upstream Embabel API documentation.
The local POC is useful for validating contracts, but its classes and names are
not intended to be PR'd as-is.
The POC public interface is `EvolvingInvocation`, parallel to
`UtilityInvocation` and `SupervisorInvocation`.
It implements the existing `ScopedInvocation` and `BaseInvocation` contracts,
inheriting `withScope`, `withProcessOptions`, `withAgentName`, `run`, and
`runAsync` rather than introducing a separate invocation shape.
`run` and `runAsync` create and start the process.
Reactive callers that need an unstarted process can use `createProcess`, publish
ingress before or after the first tick, and then drive `tick` or `run`
themselves.
The objective-authoring seam is `ObjectiveAuthor`, avoiding collision with
Embabel's existing planner abstraction.
An `ObjectiveAuthor` receives an `ObjectiveAuthorRequest` containing the
objective, additional inputs, active `AgentScope`, and `ProcessOptions`, then
returns an `ObjectivePlan`.
The POC validates authored agenda goals against the active `AgentScope` and
applies the plan's initial facts, agenda entries, and evolution policy before
process launch.
An LLM-backed `ObjectiveAuthor` should reuse Autonomy, `Ranker`,
`GoalSelectionOptions`, and `GoalChoiceApprover` for ranking and approval where
applicable.
Current Autonomy ranks existing goals; it does not author `ObjectivePlan`s.
The current POC creates the configured `AgentScope` before calling
`ObjectiveAuthor`.
Objective-dependent scope assembly before launch is future work; runtime action
or agent-scope expansion is out of scope.

The refined POC path is `EvolutionPolicy`.
It maps selected process facts to process-local runtime goals.
For example, a rule can say that an `AdditionalStorageNeeded` fact should be
handled by the scoped goal that produces `StorageCompleted`.
The target is canonicalized against the active scope before the process starts,
so a caller cannot smuggle altered goal metadata through a lookalike runtime
goal.
When a matching fact is visible at a planning tick, the policy proposes a
runtime agenda entry for the process.
The normal planner then arbitrates that runtime goal against any other active
work.
Actions that handle policy-created runtime goals must be declared as goal
producers in the active scope, for example by producing the goal's satisfied-by
type and, in annotation style, using `@AchievesGoal` where appropriate.
Standing level reactions should usually stay plain value-selected actions under
`NIRVANA`; making a level reaction an achieved goal can accidentally turn normal
utility work into process completion or agenda completion.

`GoalAgenda` is immutable.
Use `withEntry`, `withoutEntry`, or `expire` to produce a new agenda.
`GoalAgenda`, `EvolutionOptions.agendaCatalog`, raw `activationKey`,
`ActivationTrigger`, and `AgentProcess.addAgendaEntry` are low-level POC
substrate and test hooks.
They prove the process-local agenda mechanics, but normal consumers should not
need to manage activation latches or manually clear keys.
The preferred direction is: domain facts become visible to the process, then an
`EvolutionPolicy` maps selected facts to runtime goals.
An `AgendaEntryApprover` can approve or veto catalog activation or direct
runtime proposals.
It has a different request payload from `GoalChoiceApprover`, so the two should
not be collapsed directly.
Before promoting the agenda approver as a stable public API, prefer extracting
or sharing the approval response protocol shape, or document why the agenda
approver remains a parallel seam.
Once activated, an entry is projected into the process planning system without
adding a new planner type.
The selected process goal is an `AgendaPlanningGoal`, whose `entry` exposes the
agenda id, bindings, source, and completion mode.
The wrapper preserves the underlying goal name for planner semantics such as
`NIRVANA`; agenda identity lives on `entry.id`.
This lets an agenda-wrapped `NIRVANA` goal keep using Hybrid utility planning
for standing utility work.
Runtime goals compose with agenda-wrapped `NIRVANA` through normal planner
arbitration, while already satisfied runtime goals are projected without
`NIRVANA` so their completion behavior can run.
Hard interruption is best modeled as availability, not as an Evolving-specific
priority mechanism.
Consumers can use existing `@Condition` methods and `@Action(pre = ...)`
preconditions to make ordinary work unavailable while a domain condition holds,
then let hazard or recovery actions become the achievable path.
Goal and action values remain the ordinary soft arbitration mechanism when more
than one path is available.

The local POC fact-ingress seam is named `BlackboardIngress` and is available
from `AgentProcess` and `ProcessContext`.
`IngressOptions` can append facts, keep only the latest visible fact for a key,
coalesce pending ingress by key, activate catalog entries by `activationKey`,
wake blocked processes, and hide drained
facts after a TTL.
Those knobs are intentionally treated as throwaway POC detail.
For upstream design, the useful contract is a sanctioned process-local fact
ingress seam for selected external facts, likely exposed as
`process.ingress().publish(fact)` or possibly as a friendlier facts facade.
The blackboard remains process-local working memory for an `AgentProcess`, not
a mutable world-state database, pub/sub bus, or agenda latch system.
Action inputs are resolved from the blackboard, action outputs are appended to
it automatically, and planning conditions are separate booleans normally
provided by `@Condition`.
Consumer applications still own high-frequency or reversible domain state such
as sensor snapshots, tray contents, or inventory. Embabel should consume that
state through action inputs and `@Condition`; ingress is not a replacement for
application-owned state modules.
Normal Embabel planning handles the main loop from current state. Evolving
runtime goals are for side work or newly discovered objectives that need
process-local lifecycle: track, retry, complete, consume, and resume.
Blackboard objects are ordered and append-only; hiding an object removes it from
future planning and API visibility without deleting process history.
If a mutable level is modeled as a blackboard fact, the consumer owns that
fact's lifecycle unless explicit ingress lifecycle options are configured. When
the level is no longer true, hide or replace the visible fact, for example with
`Blackboard.hide(...)`, `IngressMode.LATEST`, coalescing, TTL, or a configured
level trigger. Policy-created runtime goals consume an internal rule-local
activation record on `RESUMABLE` completion; they do not infer that an arbitrary
level fact should retract just because a reaction ran.
Ingress publish is safe for external callers; blackboard writes happen when the
process drains ingress at a planning tick.
The ingress concept is distinct from `ReplanRequestedException`:
`ReplanRequestedException` is initiated by an action or tool loop that is already
running inside the process, while ingress is external async fact publication into
a running process.
Ingress is not a replacement for replanning; it covers the opposite direction of
state change.
Do not bless direct blackboard mutation as the external-ingress happy path:
`blackboard.addObject(...)` has no wake-up, fact observation identity,
duplicate semantics, planning-tick timing, or observability contract.
For selected external facts, prefer explicit ingress semantics over permanent
append-only boolean facts, then let the same `EvolutionPolicy` runtime-goal
engine handle selected work-item facts.
Activation keys are not written as blackboard planning conditions.

Agenda completion is controlled by `AgendaCompletionMode`.
`TERMINAL` completes the process when the entry's goal is satisfied.
`COMPOSITE_TERMINAL` completes the process only when its completion predicate is
satisfied. If the underlying goal is satisfied before the predicate is true, the
process waits instead of repeatedly replanning the same already-satisfied goal.
`RESUMABLE` removes the satisfied entry, consumes visible blackboard outputs
that satisfy the entry goal, consumes policy-created rule activation records,
and lets the process re-arbitrate. Catalog-created entries still hide their
explicit source fact. This prevents a later reactivation from being instantly
satisfied by stale output from the previous activation and prevents the same
fact observation from repeatedly firing the same runtime goal.
`KEEP_ALIVE` and `RECURRING` are intentionally not part of this POC surface.
`AgendaCompletionPredicate` overlaps with Embabel's existing `Condition`
composition model.
Future composite completion should decide whether it can be represented as a
`Condition`, as an adapter over `Condition`, or must remain an internal predicate
because it needs `AgentProcess`, `AgendaEntry`, and `GoalAgenda` context.

`IngressWake.WAKE` makes a `WAITING`, `STUCK`, or `PAUSED` process runnable
again. Cooperative action cancellation remains available through the existing
`AgentProcess.terminateAction` primitive, backed by
`TerminationSignal(TerminationScope.ACTION)`, but it is not a separate
Evolving-ingress wake mode in this simplified POC.

`CompletionPolicy` is separate from `EarlyTerminationPolicy`.
It returns a `ProcessOutcome`, available from `AgentProcess.outcome`.
`CONTINUE` means no terminal status transition.
`COMPLETED` maps to `AgentProcessStatusCode.COMPLETED`.
`EXHAUSTED` and `CANCELLED` map to `AgentProcessStatusCode.TERMINATED`, with the
outcome recorded as failure information.
`failureInfo` on a terminated process may therefore contain a non-error
`ProcessOutcome`; inspect `AgentProcess.outcome.code` when distinguishing
exhausted, cancelled, and failed-style terminations.
A drained resumable agenda with no remaining plan is exhausted rather than stuck.

    .withBindings(Map.of("tenant", "test"))

ObjectiveAuthor objectiveAuthor = request -> {
    var collectSamplesUntil = request.objectiveAs(JavaCollectSamplesUntil.class);
    CompletionPolicy completeWhenStored = (process, agenda) -> process.getObjects().stream()
        .anyMatch(JavaSampleStored.class::isInstance) ?
        new ProcessOutcome(ProcessOutcomeCode.COMPLETED, "sample stored", null) :
        new ProcessOutcome();

        List.of(),
        List.of(new JavaSampleAvailable(collectSamplesUntil.zone())),
